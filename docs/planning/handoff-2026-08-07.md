# Project Progress Against Original Intent

## Conclusion

Measured against the original goals, this project has completed a **security-kernel MVP**, but it has not yet completed a **limited-live system that can be independently deployed and connected to actual trading infrastructure**.

In other words:

- Core security logic such as structured intents, Reviewer, OPA/Rego, risk checks, Broker, auditing, approvals, and Kill Switch is largely in place.
- The “last mile,” including HTTP services, standalone processes, a real Binance client, complete network isolation, and live preflight, is still missing.
- It is suitable as an internal framework, prototype, and security control kernel.
- It should not currently be considered a complete production trading platform.

This is consistent with the overall assessment in `docs/planning/handoff-2026-06-15.md:158-165`.

### Current Maturity

| Dimension | Current Status |
|---|---|
| Schema, OPA Policy, security invariants | Largely complete, with good quality |
| Reviewer, Risk Engine, Broker orchestration | Core flows complete |
| Audit, Approval, Kill Switch | Core logic complete; insufficient runtime persistence and operational capabilities |
| Binance, EVM, Solana | Interfaces, simulation, and safety validation are relatively complete; real execution backends are incomplete |
| OpenClaw, Hermes | In-process adapters and examples exist; they are not complete framework plugins or service integrations |
| HTTP/API service | Not completed |
| One-command local deployment and network sandboxing | Not completed |
| `canary_live` | Policy rules exist; the complete go-live process is not completed |
| `production` | Explicitly deferred; proactively rejected by the Broker |

Verification recorded on 2026-08-07 (historical results, not current test counts):

- `pnpm run ci`: **22 test files, 579/579 passed**
- `pnpm test:integration`: **4 integration test files, 24/24 passed**
- OPA v1.16.1: **75/75 Rego tests passed**

These results demonstrated the security kernel's test status at the time, but did not demonstrate that deployment and real trading paths existed.

## Planned for the Current Phase but Not Yet Completed

### 1. Guardrail HTTP Service Layer

The original architecture selected a Sidecar Guardrail Service, but only in-process classes currently exist:

- `packages/guardrail-service/src/index.ts` only exports library interfaces.
- There is no `packages/guardrail-service/src/server.ts`.
- There are no actual:
  - `GET /health`
  - `POST /evaluate`
  - HTTP request validation
  - Header correlation ID injection
  - Endpoint tests

These tasks are still explicitly unchecked: `docs/planning/review_1.todo.md:358-367`.

**Result:** The internal logic can be called directly by code, but it cannot be deployed as an independent Guardrail API.

---

### 2. Standalone Runtime and Complete Local Docker Deployment

The original Phase 13 included local Docker, an Agent container, Broker, egress proxy, and network restrictions. Currently:

- `Dockerfile.agent` immediately reports “no standalone agent runtime entrypoint” after startup and exits.
- `Dockerfile.broker` likewise exits immediately.
- `docker-compose.yml` runs only OPA and an optional Vault dev server.
- There is no service orchestration for Guardrail Service, Broker, Agent, Signer, or egress proxy.
- There is no complete firewall, NetworkPolicy, or nginx-egress configuration.

See:

- `docs/deployment-profiles.md:7-14`
- `deploy/docker/Dockerfile.agent:22`
- `deploy/docker/Dockerfile.broker:22`

In addition, the current dev Vault publishes port `"8200:8200"`. It should not be treated as a secure deployment configuration for a cloud host.

---

### 3. Complete Preflight and First-Trade Closed Loop for `canary_live`

The Broker already has:

- A switch to explicitly enable `canary_live`
- Environment matching
- Kill Switch
- Broker revalidation
- Small-value policy limits

However, the following work from the original plan remains incomplete:

- Audit log writability preflight
- Kill Switch reachability preflight
- Approval Store accessibility preflight
- Check that the Binance API Key has no withdrawal permissions
- Binance IP allowlist configuration check
- Complete dry-run report before the first order
- Order-status reconciliation after the first order

The missing file is `packages/broker/src/preflight.ts`; see the checklist at  
`docs/planning/review_1.todo.md:230-241`.

**Assessment:** The rule kernel for canary-live currently exists, but there is not a sufficiently complete operator go-live protocol.

---

### 4. Real Binance REST Client

The current implementation includes:

- `BinanceApiClient` interface
- Paper simulator
- Connector orchestration, order parameter validation, and isolated margin checks
- Broker-side price, timestamp, slippage, and notional amount revalidation

But there is no concrete signed Binance REST client:

- `BinanceConnector` receives an external `BinanceApiClient` through its constructor
- The repository contains no client implementing that interface
- There is no implementation that calls Binance’s signed REST API

This does not meet the current-phase goal of a “thin broker-owned Binance signed REST client” in the initial design.

The following are also still missing:

- Binance HTTP-level mock integration test
- Binance sandbox/testnet order placement and cancellation tests
- API permissions endpoint check

See:

- `packages/binance-connector/src/interfaces.ts:33-41`
- `docs/planning/review_1.todo.md:281-287`
- `docs/planning/review_1.todo.md:369-375`

---

### 5. Real Balance-Delta Extraction for EVM/Solana

Resolved at the provider/connector boundary (2026-10-10):

- Sepolia uses pinned Geth execution/state-diff traces, audited ERC-20 mapping layouts,
  and pre/post balance probes. Missing trace support or unclassified effects remain refused.
- Solana uses same-slot finalized pre/simulated account snapshots for SOL and supported
  SPL amounts, with trusted decoding for real transfer instructions.
- Both connectors bind simulation to the actual signer and reject mismatched or unreliable
  balance evidence before signing. Local Anvil/LiteSVM smoke exercised real cryptographic
  signing and execution, not the synthetic `LocalDev*Signer` implementations.

See [provider configuration, asset/fee semantics, and limitations](../signing-backends.md#built-in-testnet-simulation-before-signing).
This does not add production custody backends or enable onchain execution in default Compose.

---

### 6. Persistent Runtime Mode for Approval

The following have been completed:

- Approval state machine
- approve/deny/timeout/consume
- CLI class
- Approval auditing
- Durable allowlist onboarding file storage

However, ordinary pending approvals are still stored in:

```ts
private requests = new Map<string, ApprovalRequest>();
```

See `packages/approval/src/store.ts:17-20`.

`ApprovalCli` also merely holds the same `ApprovalStore` object, with no independent database or server.

**[INFERENCE]** The original plan requires the operator to execute `list/show/approve/deny/watch` from a separate process; without a shared persistent Store, a separately launched CLI process cannot see pending approvals in the service process.

Therefore, the current approval implementation is suitable for testing and single-process integration, but not for a complete multi-process operational system.

---

### 7. Network Isolation and Egress Observability

The original plan explicitly requires:

- The Agent can access only the Guardrail and permitted data sources
- The Agent is prohibited from directly accessing Binance/RPC
- Metadata and internal network addresses are blocked
- DNS and egress attempts are logged

However, these are currently still primarily deployment requirements in the documentation:

- There is no egress proxy artifact
- There is no DNS logging
- There are no persistent or centralized egress logs
- The egress paths for LLM providers and market data sources have not yet been decided
- There is no directly deployable Kubernetes NetworkPolicy

See the incomplete items at:

- `docs/planning/review_1.todo.md:273-279`
- `docs/planning/review_1.todo.md:383-389`

This is important because “the Agent cannot directly access the exchange/RPC” is one of the core security assumptions of the entire project.

---

### 8. Remaining Integration Coverage Gaps

Current status (updated 2026-10-09): four integration test files exist:

- [OPA evaluator HTTP integration](../../packages/guardrail-service/src/opa-evaluator.integration.test.ts) uses a local mock HTTP server.
- [OPA/Rego transform integration](../../packages/guardrail-service/src/opa-transform.integration.test.ts) runs real `opa eval` only when `opa` is on `PATH`; otherwise the suite is skipped.
- [EVM Sepolia provider integration](../../packages/evm-connector/src/sepolia-provider.integration.test.ts) uses a local mock JSON-RPC server, not a live Sepolia endpoint.
- [Solana devnet provider integration](../../packages/solana-connector/src/devnet-provider.integration.test.ts) uses a local mock JSON-RPC server, not a live devnet endpoint.

However, the following are still missing:

- Binance HTTP-level connector integration
- Agent adapter → real Guardrail stack integration
- Binance sandbox/testnet integration
- Red-team and endpoint integration for the HTTP Guardrail Service

Current test gates:

- Both Vitest configurations set `passWithNoTests: false`, so empty test-file discovery fails. This does not prevent prerequisite-based skips such as the OPA transform suite.
- The unit configuration explicitly excludes `**/*.integration.test.ts` while retaining Vitest's default exclusions; the integration configuration includes only `packages/*/src/**/*.integration.test.ts`. The two commands no longer overlap.

Both CI entry points invoke integration tests: `pnpm run ci` runs lint, typecheck, unit tests, and integration tests; the `test` job in `.github/workflows/ci.yml` runs build, unit tests, and integration tests sequentially. The separate `opa-policy-test` job runs Rego policy tests but does not supply an `opa` executable to the integration-test job.

### 9. OpenClaw/Hermes Are SDK Wrappers, Not Complete Runtime Integrations

The two current adapters are essentially identical:

- They receive an in-process `GuardrailService`
- They expose controlled tool names
- They convert parameters into intents and call the service

The following were not found:

- Actual OpenClaw/Hermes framework dependencies
- MCP server
- CLI/HTTP plugin
- Agent runtime registration
- Real service-stack integration tests

Therefore, the adapter interfaces and examples have been completed, but the actual delivery for integrating with these two Agent runtimes remains relatively thin.

## Intentionally Deferred as Future Work

These should not be counted as “omissions from the project,” but as explicitly deferred scope.

### 1. Defense Against RPC Eclipse / BGP Split Attacks

This is the clearest Future Work item and is listed separately as Phase 18:

- RPC quorum service
- Multiple providers across regions and ASNs
- Compare chain ID, block number, block hash, finality, gas, and account state
- Require quorum before high-risk signing
- Confirm transaction inclusion from multiple sources
- At least one self-hosted node

See:

- `docs/planning/init.planning.md:824-845`
- `docs/planning/init.todo.md:413-426`

---

### 2. Full Production Trading and Mainnet Signing

The initial real-funds goal was small-value `canary_live`, not full production.

The current documentation explicitly states:

- `production` is a reserved/planned profile
- The Broker returns `production_not_supported` for production
- Ethereum mainnet and Solana mainnet signing are both hard-denied pending explicit future support

Therefore:

- **Incomplete canary-live preflight** is a gap in the current plan.
- **Full production and mainnet** are explicitly deferred work.

---

### 3. Custody-Grade Signing Such as KMS, HSM, MPC, and Multisig

The initial plan explicitly selected Option B rather than implementing institutional custody architecture from day one.

Future backends include:

- AWS/GCP/Azure KMS
- PKCS#11 HSM
- MPC/TSS
- Hardware wallet
- Multisig governance
- Potentially moving the security-critical signer to Rust/Go

See:

- `docs/planning/init.planning.md:451-472`
- `docs/signing-backends.md`
- `packages/secrets/src/local-signer.ts` currently has only a local/testnet implementation

This is production-grade asset custody capability, not an omitted foundational MVP task.

---

### 4. Web UI and External Approval Notification Channels

The order of approval channels was defined from the beginning as:

1. CLI first
2. Local Web UI
3. Slack
4. Telegram
5. Discord
6. WhatsApp
7. Signal

See `docs/planning/init.planning.md:543-547`.

Currently, only `ConsoleNotifier` is implemented; the other channels have only config interfaces, which is consistent with the original intent of “later adapters.”

A distinction is required:

- Slack/Web UI and similar channels not implemented: **future work**
- No shared persistence for pending approvals: **the current CLI operational goal has not yet been fully implemented**

### 5. Complete Production Deployment on VPS, Kubernetes, and Cloud

The original plan was:

- Local Docker first
- Single VPS later
- Kubernetes HA later
- HCP Vault/cloud secret managers later

The related documentation and sample configurations have now been written, but there are no complete runnable deployment assets.

Therefore:

- Missing runnable local Docker stack: a gap in the current plan
- Complete VPS/Kubernetes/cloud production manifests: future deployment work
- Documentation for Vault single-node, Kubernetes HA, and HCP: completed
- Actual environment implementation and automation: future work

---

### 6. Expanded Trading Markets and Account Modes

The following were explicitly excluded from the first phase:

- Margin lending
- Cross-margin
- COIN-M futures

These may only be supported if the scope is explicitly expanded in the future.

There are also two permanent security non-goals that should not be understood as future features:

- CEX withdrawals
- Account transfers

The README explicitly states that they are always rejected; see `README.md:15-21`.

---

### 7. Stronger Prompt Injection Defenses

The current detector uses fixed regular expressions and covers known fixtures, but it is not a complete NLP security system.

The subsequent red-team documentation recommends:

- Obfuscated and multilingual instructions
- Markdown/tool-call wrappers
- Indirect retrieved-content injection
- Combined attacks involving prompt injection + stale data/reviewer failure
- Leakage scanning against real production loggers and external sinks

See `docs/red-team-findings.md:38-50`. This is future hardening; the current regular expressions should not be understood as the final solution.

---

## Recommended Completion Order

If development continues according to the original intent, the shortest path is:

1. Implement the Guardrail HTTP Server and standalone runtime.
2. Complete the local Compose stack: Agent, Guardrail, Broker, OPA, Vault, and egress proxy.
3. Implement a real Binance signed REST client.
4. Implement live preflight, dry-run, permission/IP checks, and reconciliation.
5. Replace ApprovalStore with shared persistent storage.
6. Complete reliable balance-delta extraction for EVM/Solana.
7. Add Binance, Agent stack, and HTTP red-team integration tests.

Only after these are completed will the project move from an “internal security-kernel MVP” to a “system that can seriously begin canary-live trial operation.”

Additional note: No product code was modified in this review; only reusable lessons about test command ordering and Vitest globs were recorded in `AGENTS.md:59-62`.
